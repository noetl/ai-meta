# `repos/noetl` — what is in it that is not the thin wrapper

**Phase 1, read-only. Nothing deleted, moved, or deployed.**
Audited 2026-08-30 against `repos/noetl` **`origin/main` = `2c7a71ee`**, in a
clean worktree — the checked-out submodule was on a stale branch
(`feat/ehdb-phase-d-eventstream`, 17 commits behind), and three files the older
analysis discusses do not exist on main at all. Prod facts read live from the
cluster, read-only.

## Headline

`repos/noetl` is not a drifted wrapper. **It is the entire legacy Python
platform — 356 files, 91,678 lines** — and it contains **no wrapper at all**:
`pyproject.toml` declares **no `[project.scripts]`**, so the package installs no
`noetl` command. The `/gcp/token` endpoint is not an anomaly; it is one of **98
routes across 3 FastAPI apps**.

The wrapper that *should* exist already exists **somewhere else and is dormant**
— see "The target end-state" below.

## 2. Is this the "Python quit unexpectedly" crash source?

**The signature the owner described is not present anywhere.** Measured across
every repo, with a positive control (106 `subprocess` hits prove the scan works):

| primitive | hits, all repos |
| :-- | --: |
| `atexit` | **0** |
| `os.fork` | **0** |
| `close_fds=False` | **0** |
| `preexec_fn` | **1** |

There is **no `atexit` handler anywhere in any repo**, so the specific
"subprocess spawned at interpreter shutdown" pattern cannot be occurring.
`multiprocessing` appears once and is `shared_memory` only — no process fork.

**But the fork-forcing half does exist, in exactly one place:**

```
repos/noetl/tests/test_server_api.py:153-157
    server_process = subprocess.Popen(
        cmd, stdout=log_file, stderr=subprocess.STDOUT,
        preexec_fn=os.setsid)
```

`preexec_fn` is the decisive flag: it forces CPython to abandon `posix_spawn()`
and use `fork()` + exec, then run a Python callback **in the forked child of a
multi-threaded parent** — the unsafe-after-fork pattern macOS aborts on.

**The fix is one line:**

```python
# before
subprocess.Popen(cmd, stdout=log_file, stderr=subprocess.STDOUT,
                 preexec_fn=os.setsid)
# after — same new session/process group, no fork-time Python callback,
# and posix_spawn stays available
subprocess.Popen(cmd, stdout=log_file, stderr=subprocess.STDOUT,
                 start_new_session=True)
```

`start_new_session=True` calls `setsid` in the child via the C-level path, so the
later `os.killpg(os.getpgid(pid), ...)` teardown keeps working unchanged.

**Verdict, stated precisely rather than conveniently:** if the crashes happen
while running `pytest` in `repos/noetl`, that line is a real and fixable cause.
If they happen at any other time, **`repos/noetl` is not the source** — its
shipped code has no fork path at all — and the cause is elsewhere. I have no
evidence to name a culprit beyond that one line, and will not invent one.

## 3. The target end-state — and the surprise

The wrapper should wrap **`repos/cli`**, whose `Cargo.toml` builds binaries
**`noetl`** and **`ntl`**.

**It already exists and has never shipped.** `repos/cli/pyproject.toml` is a
complete maturin/PyO3 wheel config — `name = "noetl"`, `build-backend =
"maturin"`, `bindings = "bin"`. But **no workflow in `repos/cli` publishes it**
(0 files mention pypi/twine/maturin, against a control of 2 mentioning cargo),
and its version is pinned at **2.5.11 while the crate is at 4.22.0** — the
scaffold has drifted for whole major versions because nothing builds it.

Meanwhile **`repos/noetl` actively publishes to PyPI and GHCR** — its
`build_on_release.yml` ran green on **2026-08-18**, twelve days ago, shipping
`noetl` **4.26.1** plus `ghcr.io/noetl/noetl:latest`.

> **So the PyPI name `noetl` is currently owned by the thing to be retired, and
> the wrapper meant to own it is dormant.** That inversion is the central fact
> of this migration: it is a *distribution* handover, not just a deletion. It
> also explains the version numbers — 4.26.1 (legacy) is far ahead of 2.5.11
> (wrapper), so a naive cutover would publish a **version regression** to PyPI.

`9bf82fc4 chore(retire): remove Python CLI shim modules superseded by the v5
wheel` already deleted `main.py` / `install.py` / `cli_wrapper.py` — so the shims
went before their replacement was published. Three docs still say
`python -m noetl.main`, which now names a module that does not exist.

## 4. Removal / relocation plan

Nothing here is executed. Every item is recoverable from git history; the
"only lives here" column is the one that matters.

### 🔴 STILL-LIVE — stop, do not delete

| item | why |
| :-- | :-- |
| `noetl/database/ddl/postgres/schema_ddl.sql` | **The Rust stack depends on it.** 29 references in `repos/ops`; the Rust server cites it as the schema definition in 6 comments (`server/src/main.rs:1231`, `db/queries/catalog.rs:13`, `event_chain.rs:11,27,74`). The Rust server does not own its schema. **Only lives here.** Deleting breaks the deploy. |
| PyPI + GHCR publication | Released 12 days ago. External `pip install noetl` users get 4.26.1 from this tree. Removing the package content changes a public artifact — needs a deliberate handover, not a delete. |
| `ghcr.io/noetl/noetl` image consumers | `ops/automation/gcp_gke/noetl_gke_fresh_stack.yaml`, `agents/noetl/lifecycle/bump_image.yaml`, and `deploy_gke_stack.yaml` (`build_noetl: true`, "Python NoETL — same image for server AND worker"). Prod does not run it, **but a fresh-stack or DR apply would build and deploy Python.** Same hazard class as #309. |

### 🟡 NEEDS-RELOCATION — move, do not drop

| item | destination |
| :-- | :-- |
| `schema_ddl.sql` | Schema ownership into `repos/server` (or an owned migrations home). This is the unlock for retiring `noetl/database/` — a deliberate decision, not packaging cleanup. |
| `core/dsl/_generate_schema` (13k-line DSL tree) | The DSL-schema generator is invoked as `python -m noetl.core.dsl._generate_schema` in 4 places. Needs a home before `core/` can go. |
| `core/auth/ib_provider` + `core/auth/providers` | The only real cross-repo Python consumer: `repos/e2e/fixtures/playbooks/oauth/interactive_brokers/validate_implementation.py`. (5 of the 8 apparent e2e "imports" were SQL `from noetl.event e`, not Python — the same false-positive class as #207.) |

| item | evidence |

⚠ "Safe to delete" here means *safe as code*. All of it still ships to PyPI
today, so deletion changes the published package — sequence it with the
distribution handover, not before.

### Sequence

1. **R-0 (do first, independent of everything):** fix
   `tests/test_server_api.py:157`. One line, no coupling, and it answers the
   crash question empirically.
2. **R-1 distribution handover.** Publish the `repos/cli` wheel, resolve the
   version collision (must exceed 4.26.1), point `noetl` on PyPI at the wrapper.
   **Everything else is gated on this** — until it lands, deleting Python
   content silently degrades a live public package.
3. **R-2 docs truth-up.** Remove `python -m noetl.{main,outbox,projector}` from
   docs. `main` is already broken.
4. **R-3 ops de-risk.** Neutralise `build_noetl: true` and the
   `ghcr.io/noetl/noetl` deploy paths so no fresh-stack/DR apply can resurrect
   Python. Independent of R-1 and worth doing early.
5. **R-4 schema relocation.** Move `schema_ddl.sql` ownership into `repos/server`.
6. **R-5 bulk retirement.** `server/`, `worker/`, `tools/`, `outbox/`,
   `projector/`, `claim_policy.py` — one `chore(retire):` commit per tree,
   following the `noetl#691` precedent. **176 test files** reference these and
   must be deleted or re-pointed first; that test migration is the real cost.
7. **R-6 `core/`.** 37,399 lines, 79 test files. Its own umbrella, not part of
   this.
