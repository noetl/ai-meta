## Step 2 — the stop

> *"If the Rust side has NO complete playbook model (only parses ad hoc), STOP
> and report that gap."*

The Rust side has **three** playbook models, none complete, and the part they
all omit is the part a third of real playbooks use.

### The three models

| # | crate | file | lines | root fields |
| :-- | :-- | :-- | --: | :-- |
| A | `noetl-executor` (`repos/cli/executor`) | `src/playbook.rs` | 527 | apiVersion, kind, metadata, **executor**, workload, workflow |
| B | `noetl-orchestrate-core` (`repos/server`) | `src/playbook.rs` | 1802 | apiVersion, kind, metadata, workload, **vars**, **keychain**, **workbook**, workflow |
| C | `noetl-executor 0.5.0` **from crates.io** | — | — | whatever 0.5 shipped |

- **A is what the CLI runs.** `repos/cli/src/playbook_runner.rs:224` does
  `serde_yaml::from_str::<Playbook>`.
- **B is what the server uses.** `repos/server/src/playbook/mod.rs:13` —
  `pub use noetl_orchestrate_core::playbook as types`.
- **C is what the shipped worker uses.** `repos/worker/Cargo.toml:232` declares
  `noetl-executor = "0.5"` and `Cargo.lock` resolves it to **0.5.0 from
  crates.io** — not the local 0.8.0. A range is a decision made later by a
  resolver, and this one picked a different copy of the model.

A and B disagree on **4 of 8 root fields**: `executor`, `keychain`, `vars`,
`workbook`. Neither is a superset of the other.

Both are **permissive** (`deny_unknown_fields` appears in neither), so they do
not reject each other's fields — they silently ignore them. That is why this
has never produced a visible failure.

### What all three omit

The DSL's **policy layer has no Rust type anywhere.** Searched all three crates
plus `repos/server/src`, name-agnostically, against a positive control (`Step`
found 1/1, so the search works):

| Python `$def` | any Rust type? |
| :-- | :-- |
| AdmitPolicy, ExecutorPolicy, FramePolicy, StepPolicy, TaskPolicy, LoopPolicy | **none** |
| CursorSpec, OutputStore, OutputSelect, OutputAccumulate, ToolOutput, Arc, TaskSpec | **none** |

The only Rust types matching `*Policy` are `Policy` (an HTTP route policy in
`server/src/handlers/db_routes_policy.rs`) and `CleanupPolicy` (a cleanup
config) — neither is DSL policy.

Even with deliberately generous fuzzy matching (allowing `LoopConfig` to stand
for `Loop`/`LoopSpec`/`LoopPolicy`, `Executor` for `ExecutorPolicy`, and so on),
coverage is **14/24 for A** and **12/24 for B** — and the unfakeable absences are
the entire output surface (`OutputStore`/`OutputSelect`/`OutputAccumulate`) and
task policy.

### This is not dead surface — 61 real playbooks use it

Across 202 playbook files in `repos/e2e/fixtures`, `repos/ops/playbooks`, and
`playbooks/`:

| construct | files using it |
| :-- | --: |
| `policy:` | **61** |
| `loop:` | 39 |
| `keychain:` | 13 |
| `workbook:` | 5 |
| `cursor:` | 4 |

`policy:` is in **30% of real playbooks**.

### How Rust handles it today: ad hoc, by string key

Not ignored — read untyped at runtime:

- `repos/tools/src/tools/task_sequence.rs:308` — `.and_then(|s| s.get("policy"))`
- `repos/server/orchestrate-core/src/commands.rs:849` — builds
  `spec.policy.rules` as raw `serde_json::json!`

So the policy layer flows through as untyped JSON, addressed by string literal.
That is precisely "parses ad hoc", and it is why `schemars` cannot see it:
`#[derive(JsonSchema)]` can only describe types that exist.

## What a schema derived today would actually say

Deriving from A (the only model the CLI can reach — `repos/cli/Cargo.toml` has
**no** dependency on `orchestrate-core`, which is a server-workspace path crate
at version 0.1.0, unpublished) would produce a schema that:

- covers 6 of 8 root fields (no `keychain`, no `workbook`);
- describes **`next:` as `any`**, because `Step.next` is
  `Option<serde_yaml::Value>` and the routing types (`NextArc`, `NextRouterSpec`,
  `NextFormat`) are built by hand in `from_yaml_value`, not by serde;
- says **nothing at all** about `policy:`, the output surface, or task specs.

Shipping that as "the NoETL playbook schema" would be a representation that
claims to describe the DSL and does not — the exact drift class the
`representation-drift` rule exists for. Editors would autocomplete a third of
the language and silently offer nothing for the most error-prone third.

## The decision this needs

Three options, in increasing cost:

1. **Ship the partial schema anyway**, titled honestly (e.g. *"NoETL playbook —
   structural subset"*), documenting that `policy`, `next`, and the output
   surface are unconstrained. Cheap, immediately useful for the structural
   fields, and honest — but it is a permanently partial artifact, and the old
   schema was strictly richer.
2. **Model the policy layer in Rust first**, then derive. This is the real
   "Rust equivalent", and it is the bigger decision you anticipated: it means
   adding ~11 types to a crate, and deciding **which** crate — which forces the
   A-vs-B question, because a schema is only meaningful if it matches the model
   that actually validates.
3. **Reconcile A/B/C first.** Arguably prerequisite to (2): today the CLI, the
   server, and the shipped worker each parse playbooks with a different model.
   Whichever one grows the policy types becomes the de-facto authority, so that
   choice should be deliberate rather than a side effect of where the schema
   work landed.

My recommendation is **(1) now, (3) then (2) as a tracked follow-up** — a
partial-but-labelled schema restores most of the editor value immediately and
costs nothing if the model is later unified, whereas (2) done inside the wrong
crate would entrench the three-model split.

⚠ Independent of the schema: **the three-model split is itself worth an issue.**
The CLI, the server, and the deployed worker do not agree on what a playbook is,
and because all three are permissive, a playbook that one silently ignores will
never raise an error — it will just not do what it says.

## Not done

Steps 3-5 (schemars derive, `noetl schema` subcommand, validation sweep,
CI staleness guard) are not started, pending the decision above.
