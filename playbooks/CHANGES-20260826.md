## ⚠⚠ READ THIS BEFORE ANY SERVER ROLLBACK

**Restore a *static* `auth0_client` credential BEFORE rolling the server image
back to v3.88.0 or earlier.**

`auth0_client`'s value is now sourced from Secret Manager via a marker inside its
encrypted `data`. **v3.89.0 understands that marker. v3.88.0 does not** — it would
serve the marker object *itself* as the credential, so
`{{ keychain.auth0_credentials.client_secret }}` would resolve to nothing and
every Auth0 call would fail with a 401 that looks like a wrong credential rather
than a version mismatch.

Correct order:

1. restore a static `auth0_client` (§8 rollback), **then**
2. roll the image back.

Rolling the image first is the failure mode this warning exists to prevent.

## 1. EHDB read-source activation — control flow recovery now reads EHDB

**What changed.** Three settings, applied together because any one alone is
broken: the server's spine query was repointed from the user pool (which runs no
state builder) to the system pool (which does); both system pools were armed to
accept server-authored projection appends; and the read source was flipped.

**Why all three.** Repointing alone breaks the C1 shadow mirror — the user pool
carries `MIRROR_SOURCE=server` and the system pools did not, so the mirror got
`501 Not Implemented`. Flipping alone leaves every recovery `spine_refused`,
because the server was asking a pool with an empty index.

**Evidence.** On-prod equivalence 4/4 before the flip and 3/3 after, digests
byte-identical, `verdict=match`. `noetl_ehdb_projection_read_total{outcome="served_tier"}`
is non-zero — reads are genuinely served from the tier, not silently falling
through. Fail-closed demonstrated itself organically:
`refold_total{verdict="spine_refused"}` fired live and **demoted rather than
serving**.

**Refs.** noetl/ai-meta#265 · server#358 (v3.88.0) · RFC §9 in
`docs/rfc/ehdb-event-sourced-control-flow.md`

### Rollback

```bash
# 1. the flip alone — safest partial rollback; returns control flow to Postgres
#    and leaves the C1 shadow working
kubectl --context $CTX -n noetl set env deploy/noetl-server-rust \
  NOETL_EHDB_PROJECTION_READ_SOURCE-

# 2. the repoint (only if also reverting the mirror arming, and in this order)
kubectl --context $CTX -n noetl set env deploy/noetl-server-rust \
  NOETL_EHDB_WORKER_QUERY_URL=http://noetl-worker-rust-metrics.noetl.svc.cluster.local:9090

# 3. the mirror arming — LAST. Reverting this before step 2 re-breaks C1.
kubectl --context $CTX -n noetl set env deploy/noetl-worker-system-pool \
  NOETL_EHDB_PROJECTION_MIRROR_SOURCE-
kubectl --context $CTX -n noetl set env deploy/noetl-worker-system-pool-shard1 \
  NOETL_EHDB_PROJECTION_MIRROR_SOURCE-
```

⚠ Unsetting `READ_SOURCE` is safe on its own: unset means `postgres`, and a typo
also lands on `postgres` (guarded by
`a_typo_still_lands_on_the_incumbent_not_on_wal`).

## 2. The twelve-day OOM — root cause fixed, mitigation then right-sized

**What was wrong.** Both system pools OOM-crashlooped from 2026-08-14, `exitCode
137`, accelerating (162 restarts in 12 days on one pod, 42 in 3 hours on
another). Nothing paged: the pool that was down runs the state builder, both
materializers and the projection mirror, and prod carries no user traffic.

**The cause was not the replay.** `ChangeFeed::poll` returned the whole tail
after the cursor in one `Vec`, serialised into **one frame**; at cursor 0 that is
the whole log. Measured from cgroup `memory.peak`: **3313 MiB** peak against a
2 GiB limit, settling to 112 MiB — a ~30× spike over the index it produces.

⚠ A memory bound *was* configured and *was* working the whole time
(`NOETL_STATE_INDEX_MAX_BYTES`, 112 MiB resident against a 256 MiB ceiling). It
bounds the **resting index**; nothing bounded **delivery**. Every configured
limit read healthy while the pod died — which is why twelve days passed.

**The fix.** ehdb#318 bounds the batch (`EHDB_FEED_BATCH_LIMIT`, default 2000)
and caps the frame reader (`EHDB_FEED_MAX_FRAME_BYTES`, default 64 MiB).
Deliberately **not** a snapshot or acked cursor: a persisted cursor that outruns
a freshly-emptied index is the noetl/ai-meta#119 stall, so that would trade a
loud crash for a silent wedge.

**Result on prod's real log: 3313 MiB → ~507 MiB.**

**Sequence.** Phase 1 raised the limit 2Gi → 8Gi as a mitigation (peak was
unbounded then). After the fix landed, §5 right-sized it to 3Gi.

**Refs.** noetl/ai-meta#298 · ehdb#318 · worker#284 (v5.122.2) · ops#273

### Rollback

```bash
# raise the limit back (does not revert the code fix)
kubectl --context $CTX -n noetl patch deploy noetl-worker-system-pool --type strategic -p \
 '{"spec":{"template":{"spec":{"containers":[{"name":"noetl-worker","resources":{"requests":{"cpu":"1500m","memory":"8Gi"},"limits":{"cpu":"2","memory":"8Gi"}}}]}}}}'
# repeat for noetl-worker-system-pool-shard1

# disable the batch bound (restores the pre-fix unbounded frame — do NOT do this
# at 3Gi; it is what OOMed at 2Gi)
kubectl --context $CTX -n noetl set env deploy/noetl-worker-system-pool EHDB_FEED_BATCH_LIMIT=0
```

⚠ `EHDB_FEED_BATCH_LIMIT=0` means **unbounded**. It is a deliberate operator
opt-out and it re-arms the original failure. The 3Gi limit was chosen with that
in mind (5.6× the measured peak, 3.6× worst case including a full 320Mi
`/dev/shm`), but do not set it without reading #298.

## 3. #297 — the silent claim-loop stall

**What was wrong.** On a deadline miss against a peer that had not proven it
heartbeats, all three read loops set `read_deadline = None`. "Let keepalive own
liveness" was not a fallback — it was an **unbounded park**, and keepalive is
answered by a live-but-stuck kernel, which is exactly the case the heartbeat
exists to catch. Pod `Running`, `1/1`, probes green, nothing logged, dispatch
stopped.

**The fix.** A miss now demotes to `EHDB_READ_HARD_CEILING_MS` (default 300 000)
instead of disarming; a second miss redials. Fixed at all three read loops:
command-bus claim, state-builder drain, group claims. Plus a claim-loop liveness
gauge and a `/livez` backstop.

⚠ The kind fault arm found **two defects in the instrumentation itself** before
they shipped: a reconnect to a frozen peer was counted as progress (8 failures
deep, gauge still healthy), and keying recovery on claims left a recovered-but-idle
pool at 503 forever — which would have restart-looped a healthy worker. The
discriminator is now *ongoing failure*, not absent claims.

**Refs.** noetl/ai-meta#297 · ehdb#319 · worker#285 (v5.122.2)

### Rollback

```bash
# disable the ceiling (restores the unbounded park)
kubectl --context $CTX -n noetl set env deploy/noetl-worker-system-pool EHDB_READ_HARD_CEILING_MS=0
# relax the livez backstop instead of disabling it
kubectl --context $CTX -n noetl set env deploy/noetl-worker-system-pool NOETL_CLAIM_LOOP_UNHEALTHY_SECS=3600
```

## 5. Memory right-size, 8Gi → 3Gi

Measured post-fix boot peak **511 / 504 MiB**; resting 42–60 MiB. 3Gi is 5.6× the
peak and 3.6× the worst case with a full 320Mi `/dev/shm`. `request == limit` so
the scheduler reserves the spike and a pod that cannot get it **fails to schedule
loudly** rather than OOMing 20s into every boot.

cpu 1500m → 750m: the 1500m was never a CPU need, only Autopilot's 1:6.5
cpu:memory ratio at 8Gi. Reclaims 5120 MiB + 750m per pool, ×2 pools.

**Refs.** ops#273 · rollback in §2 above.

## 8. `auth0_client` sourced from Secret Manager (2026-08-27)

**What changed.** The credential record keeps its identity, alias and type; only
its **value** is fetched at serve time from GCP Secret Manager
(`shastaratech-noetl-prod/auth0_client`) via Workload Identity. Playbooks are
untouched — `get_auth0_token` still reads
`{{ keychain.auth0_credentials.client_secret }}`.

Marker, inside the credential's encrypted `data`:

```json
{"__secret_source__": {"provider":"gcp","secret":"auth0_client","project":"shastaratech-noetl-prod"}}
```

**Why this shape.** The obvious design — `provider: gcp` on a playbook's
`keychain:` block — is **unreachable**: the worker never calls a keychain-resolve
endpoint, so the template renders empty and fails later as a 401. Measured in
kind before building anything else.

**Evidence.** The SM-sourced value is **field-identical and digest-identical** to
the static value it replaced — all **7** fields (`audience`, `client_id`,
`client_secret`, `domain`, `grant_types`, `token_endpoint`, `userinfo_endpoint`),
compared inside the pod, never printed.

**Latency/failure.** 10s provider timeout, 300s in-process cache
(`fetched=1, cache_hit=6` — one SM call per TTL, not per dispatch), fail-closed
with a named error on fetch failure.

**Refs.** noetl/ai-meta#267 · server#361 (**v3.89.0**) · server#360 closed,
folded in.

### Rollback

`auth0_client_sm` is retained as the value-free lever: it is SM-sourced and
digest-identical, so consumers can be pointed at it by parameter
(`auth0_credential=auth0_client_sm`) with no value handling.

To restore `auth0_client` to a static value, re-register it from the SM copy —
the value provably still lives there:

### Two things that bit

1. The GKE add-on registers its driver as **`secrets-store-gke.csi.k8s.io`**, not
   the upstream `secrets-store.csi.k8s.io`. The upstream name fails the mount with

2. **Workload Identity needs both halves.** The owner's IAM grant let the KSA
   impersonate the GSA, but the KSA carried no `iam.gke.io/gcp-service-account`

does not report the *removal* of an annotation absent from `last-applied`, so
while it was undeclared the diff was a clean no-op **and** a re-apply would have
dropped it. The no-op diff is necessary, not sufficient — the exact failure mode
noetl/ai-meta#267 exists to prevent. Re-proved no-op on all four files after the
change.

```bash
# 3. image rollback, only if needed.  ⚠ ORDERING: see the warning at the TOP of
#    this document -- restore BEFORE downgrading past the auth0 marker.
kubectl -n noetl set image deploy/noetl-server-rust \
  noetl-server=us-central1-docker.pkg.dev/shastaratech-noetl-prod/noetl/server-rust@sha256:02c1086c737d072fff8053dd6f7b2442236f4e2dd81b9837525793bdff96318b
```

⚠ The server metrics are on **8082**, not a separate 9090, and the container is
**`noetl-server`**.

### Two observations, neither blocking

- **The Postgres password is short enough to warrant rotation.** Its length is
  deliberately not recorded here — ai-meta is public, and a password length
  narrows an attacker's search space. The SM copy and the k8s copy are
  byte-identical (compared by digest, inside the pod), so this stage changed
  nothing about it; it was already this way. Rotation is an owner decision,
  tracked separately.
- **The server does not pin the `secret_source_total` label set** the way the
  worker does — only the outcome that occurred is emitted, so `file_unusable`
  is absent rather than 0. The failure mode is still visible (it would appear as
  `file_unusable=1` alongside `env=1`), and `build_info` disambiguates "absent
  because old binary". Lower grade than the gateway case, but the same family.

## 12. Stage 5 — Secret Manager is the SOLE source (2026-08-27)

**The migration is complete.** All four `secretKeyRef` bindings removed across
three workloads. `NOETL_ENCRYPTION_KEY`, `POSTGRES_PASSWORD` and
`NOETL_INTERNAL_API_TOKEN` now reach the processes **only** as CSI-projected
Secret Manager files. **There is no env fallback left.**

### The pre-flight that made it safe

Before removing anything, each mounted file was compared **by digest** against the
`secretKeyRef` value it replaced, computed inside the pod so no value transited a
terminal. All five matched.

That is the load-bearing step: a match means removing the env **cannot** change
the effective value, so the removal is a change of *plumbing*, not *content* — and
any failure afterwards is a delivery failure rather than a wrong credential.

### Staged least-critical first, each with its own gate

| # | removal | gate | result |
| :-- | :-- | :-- | :-- |
| 1 | shard1 token | source, health | `file`, healthy |
| 2 | main pool token | claim loop + indexing | connected, 78 indexed |
| 3 | server token | health | ok |
| 4 | server **encryption key** | **decryption** | payloads still decrypt to structure |
| 5 | server **pg password** | **Postgres connects** | pool created 16:05:54.013, after the three `source="file"` lines at 16:05:53.960 |

Real e2e executions reached `COMPLETED` (13 events) after the pool removals and
again after the full server removal. `restarts=0` everywhere.
`READ_SOURCE=wal` + event-log primary unchanged.

### The file is genuinely the only source

All three variables are now **absent from the container environment entirely** —
kubelet no longer injects them — so the values the process holds can only have
come from `/var/secrets/sm`.

### Rollback — re-add the secretKeyRefs

Written **before** the removal, not reconstructed after:
`playbooks/secret-manager/STAGE5-ROLLBACK.md`.

The k8s Secrets `noetl-secret` and `noetl-internal-api-token` are **deliberately
not deleted** — they are the re-add source.

⚠ `POSTGRES_PASSWORD` bound to the **`NOETL_PASSWORD`** key, not the
identically-named unused `POSTGRES_PASSWORD` key in the same Secret
(noetl/ai-meta#300). Re-adding against the obvious-looking key gets a wrong
password.

⚠ While a `_FILE` var is set the **file wins**, so re-adding the env restores a
*fallback* rather than moving the source back. To force the env path, unset the
`_FILE` var too.

### Consequence for rotation

Secret Manager is now the sole source, so the Postgres-password rotation
(noetl/ai-meta#304) needs **only a new SM version** — the k8s Secret no longer
feeds any running process. Not done here; owner's call.
