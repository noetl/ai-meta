## ⛔ NEW BLOCKER — the catalog serves from two divergent stores

`POST /api/catalog/list`, six consecutive reads, seconds apart:

```
read 1: entries=2533  duffel_latest=v7   flights-details=[1]     <- store A
read 2: entries=1370  duffel_latest=v19  flights-details=ABSENT  <- store B
read 3: entries=1370  duffel_latest=v19  flights-details=ABSENT
read 4: entries=1370  duffel_latest=v19  flights-details=ABSENT
read 5: entries=1370  duffel_latest=v19  flights-details=ABSENT
read 6: entries=1370  duffel_latest=v19  flights-details=ABSENT
```

The two stores have **independent version histories for the same paths**:

| path | store A | store B |
|---|---|---|
| `automation/agents/mcp/duffel` | v1–v7 | v1–v19 |
| `automation/agents/mcp/hotelbeds` | v1–v6 | v1–v8 |
| `muno/playbooks/hotel-cards` | v1–v4 | v1–v5 |
| `muno/playbooks/itinerary-planner` | v1–v17 | v1–v113 |
| `muno/playbooks/flights-details` | v1 | ABSENT |

Store B's latest content for duffel / hotelbeds / hotel-cards does **not** match
`main` either — so B is not simply "A plus more".

**Consequence:** `POST /api/execute` resolves against store B, so
`muno/playbooks/flights-details` → `404 "Playbook not found"`, while
`muno/playbooks/hotel-cards` dispatches fine (it exists in both).

This matches the `noetl_server::ehdb_parity: EHDB cross-store parity DIVERGENCE`
warnings the server emits continuously.

⚠ **Before the writer restart, catalog reads were stable** (2529 → 2533 across
several reads during registration). The flap appeared only afterwards. The
restart plausibly re-opened the tier store and exposed B alongside A. Recorded as
an observation, **not a proven cause** — per this loop's cadence.

## STOPPED here, deliberately

Re-registering into a flapping catalog would write a v20/v9/v6 into whichever
store answers, without any way to verify which one wins. That compounds a
data-consistency split rather than fixing it, and picking a winner between two
divergent histories is a data decision the owner owns.

Not done: no second writer, no frame-cap code change/release, no PVC or
event-data mutation.

## Open question for whoever picks this up

Which store is authoritative, and why does `/api/catalog/list` alternate? Until
that is answered, **registration results cannot be trusted** — an entry can be
verified present immediately after writing and be absent on the next read.
